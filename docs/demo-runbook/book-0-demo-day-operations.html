2. The evening before — build the demo database

This produces the same database every time: the same 103 people with the same staff numbers, the same open requests, the same items in every approval queue. If a rehearsal leaves junk behind, rebuild and it is gone. Takes about five minutes.

1Stop anything runningClose any window running the API or the web app (Ctrl+C in each).
2RebuildIn PowerShell, at the repository root:
powershell -File .\scripts\New-UatDatabase.ps1
Type ErpSystemDB_UAT when it asks. Wait for the counts.
3Read the countsYou should see these lines. Any zero under "demo dataset" means a seeder failed — scroll up for the line reading FAILED:.
Employees             = 127
Leave types           = 9
Public holidays       = 26
Units with a head     = 38
Demo staff (TDC/...)  = 103
Demo logins (linked)  = 8
HR workflow defs      = 16   (of 25 seeded; the count line checks a subset)
4Start the API, then load the transactions
powershell -File .\scripts\Start-ErpApi.ps1 -Database Uat
Wait for Listening : http://localhost:5000. In a second window:
cd "D:\Rhema\TDC ERPS\dev-harness\hr-demo-smoke"
node scenarios.mjs
Ends with SCENARIOS: 21 ok, 0 failed. This raises the leave requests, travel, requisitions, cases and everything else that sits in the approval queues — through the real API, as the real personas.

Then, for Book 1 §1.3:
node make-employee-import-file.mjs
Writes out\demo-employee-import.xlsx — the import template downloaded from this database and filled with six DEMO-00n rows. It creates nothing; the rows are only written when the presenter commits them on stage. (Needs python with openpyxl.)
5Start the scanner and prove an upload
powershell -File .\scripts\Start-DemoVirusScanner.ps1
Then in the app, attach any PDF to a draft policy (Book 3 §10). If it saves, every other upload in the module will too — they all go through the same gate.
5bProve the logins
node personas.mjs
Eight lines, each login OK | profile 200.
6Optional — prove every screen opens
node smoke.mjs --user hr.head
Ten minutes. The last line must read 0 crash. This is the check that catches a screen that has started failing since the last rehearsal.
Never run anything from dev-harness\hr-*\ (the test suites) against the demo database. They create fixtures named Actor… and Lane4 Leave 194151. Only hr-demo-smoke\ is safe. If a suite has touched it, rebuild (step 2).

3. Demo day — bringing it up

3.1 The API

cd "D:\Rhema\TDC ERPS\RHEMA-ERP"
powershell -File .\scripts\Start-ErpApi.ps1 -Database Uat
Three lines: Database : ErpSystemDB_UAT · Environment : Staging · Listening : http://localhost:5000. Leave this window open and minimised. Staging is correct — in Development, every refusal shows a stack trace instead of the message.

3.2 The document scanner (needed for every file upload)

cd "D:\Rhema\TDC ERPS\RHEMA-ERP"
powershell -File .\scripts\Start-DemoVirusScanner.ps1
Ready. HR document uploads will now be accepted. If something is already answering it says so and leaves it alone.

Without this, every document upload in the HR module is refused — measured, not assumed: the upload returns FILE_VIRUS_SCAN_INCOMPLETE — "Upload rejected because a clean virus-scan result was not obtained." That affects all 29 HR upload categories: employee documents, policy documents, medical claims, offer letters, separation files, SHE controlled documents, evidence on a disciplinary case — every one. A clean malware scan is mandatory in the product and a tenant cannot switch it off, which is the right design and the reason this step exists.

This stub is not a virus scanner — it reports every file as clean. It is for a demo laptop and nothing else. Never say on stage that files are being scanned. If asked, see §5.

3.3 The web app

cd "D:\Rhema\TDC ERPS\RHEMA-ERP\frontend"
npm run dev
Ready on http://localhost:3000 in about fifteen seconds. First open of each screen compiles it (one to three seconds) — pre-open the screens for the first two books before the audience arrives so nobody watches a spinner.

3.4 The check that stops you demoing the wrong data

Run this once the API is up. It signs in and counts employees.

Invoke-RestMethod -Method Post -Uri 'http://localhost:5000/api/auth/login' -ContentType 'application/json' `
  -Body '{"username":"admin","password":"Admin123!"}' |
  ForEach-Object { Invoke-RestMethod -Method Post -Uri 'http://localhost:5000/api/hr/Employees/paged?page=1&pageSize=1' `
    -ContentType 'application/json' -Body '{}' -Headers @{ Authorization = "Bearer $($_.token)" } } |
  Select-Object -ExpandProperty totalCount
ResultMeaning
127Demo database. Proceed.
~1,750Development database — full of test robots. Stop the API and restart it with -Database Uat.

4. Browsers — one window per persona

Signing out and in again on stage is slow and error-prone. Instead, open one browser window per persona before the demo and switch windows.

1Main windowNormal Chrome/Edge window → http://localhost:3000/login → hr.head.
2Manager windowNew InPrivate / Incognito window → head.dev. (A private window has its own session, so both stay signed in.)
3Employee windowA second browser (Edge if the first was Chrome, or a different Chrome profile) → staff.
4As neededshe.officer, she.manager, md.tdc, new.hire, gm.ops, auditor — open when their book says so; each in a fresh private window or profile.
Sessions are JSON Web Tokens carrying the user, the tenant and the linked employee. Two private windows are two independent sessions; a normal window and a private window of the same browser are also independent. Tokens expire — if a window that has sat idle for over an hour answers "Unauthorized", sign in again in that window.

5. Rules of the road

Never click on stage: Leave → Year-End (carry-over and forfeiture rewrite every balance) · any Delete · Administration → any Reminder Engine → Run now · Sign out in a shared window · the Payroll menu (another team's module; not part of this demonstration).
If someone asks…Say
"Are these real people?""No. The organisation is TDC's real structure — every unit and every established post is from the organogram. The people are synthetic, generated to fill it, so nothing personal is on screen. Real staff records load from the employee file through the import you will see in Book 1."
"Are these real salaries / leave rules?""Placeholder figures on the real grade structure. The leave entitlements follow the Labour Act floors; TDC's own policy replaces them through the screens in Book 2 §1 — nothing is hard-coded."
"What about payroll?""Payroll is a separate module by a separate team. HR reads from it — you will see grades and pay components — and hands it attendance, deductions and claims. It is not part of today's walk-through."
"Are files virus-scanned?""Yes — and it is not optional. Every one of these upload types requires a clean scan result before the file is stored, and a tenant administrator cannot turn that off. On this laptop the scanner is stubbed so we can show you the flow; a real deployment points the same gate at a ClamAV daemon." Do not claim files are being scanned here.
"Can I try?"Yes, in the staff window. Raising a leave request or clocking in is safe and quick. Steer away from Administration.

6. When something goes wrong

SymptomCauseFix (under two minutes)
Page says "Network error" or spins for everThe API window closed or crashedRe-run §3.1. Refresh the page. Sessions survive an API restart.
"Unauthorized" after a screen that was workingToken expired (idle over an hour)Sign in again in that window only.
A list that should have rows is emptyWrong database, or the scenarios were not run after a rebuild§3.4. If it says 127, run node scenarios.mjs (§2 step 4) — it is safe to re-run; it completes what is missing.
"No active workflow definition found for entity type …"Database rebuilt with an old buildRebuild (§2) with the current build. The HR workflow definitions are seeded by seed-workflows.
"Workflow entity type … is not configured"The entity-type catalogue was not seededRun node scenarios.mjs — its first action seeds the catalogue — or, as admin in any window, open Workflow → Entity Types → Seed defaults.
"Your user account is not linked to an employee record"You are in the admin windowSwitch to the persona window the book names. This message is correct behaviour.
"You are not the direct manager of this employee"Wrong manager windowApprovals for staff and new.hire are head.dev's. Requisitions and travel above him are gm.ops's.
A refusal appears as a red stack traceAPI started in DevelopmentRestart with §3.1 exactly (Staging is the default).
Port 5000 already in useAn API is still running
Get-CimInstance Win32_Process -Filter "Name='dotnet.exe'" |
 Where-Object { $_.CommandLine -like '*ErpSystem.Api*' } |
 ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
then §3.1.
An upload is refused: FILE_VIRUS_SCAN_INCOMPLETEThe document scanner is not running (a reboot loses it)Run §3.2, then retry the upload. Nothing else needs restarting.
