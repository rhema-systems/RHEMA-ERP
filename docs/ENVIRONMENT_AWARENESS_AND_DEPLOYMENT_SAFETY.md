# Environment awareness and deployment safety

## Purpose

RHEMA-ERP presents one server-authoritative application environment before and after sign in. This prevents a browser URL, frontend build mode, or an implicit framework default from making a Test, UAT, Staging, or Development deployment look like Production.

Supported application environments are `Production`, `Test`, `UAT`, `Staging`, and `Development`. Any missing or unsupported value becomes `Unknown`. Unknown is a visible unsafe state and is never treated as Production.

## Audit findings

### Configuration before this feature

- ASP.NET Core already used `ASPNETCORE_ENVIRONMENT` / `DOTNET_ENVIRONMENT` for framework configuration selection.
- API configuration files also contained `Application:Environment`, but the value was not exposed through a safe runtime contract or used consistently by the frontend.
- `NODE_ENV` controlled Next.js build behavior. `NEXT_PUBLIC_API_URL` selected the API origin. Neither is a deployment environment authority.
- The release manifest already recorded the release environment, exact commit, release ID, build ID, and build time.
- The Windows test VPS workflow explicitly passed `-Environment Test` into build and deploy scripts, but the API service did not persist that stage as a browser-visible runtime identity.
- Login appearance was available through a public safe config route, while no equivalent environment/build descriptor existed.

### Authoritative source

`Application__Environment` is the user-facing environment authority. `ASPNETCORE_ENVIRONMENT` remains a separate framework profile and may legitimately be `Production` on a hardened Test or UAT host.

The public endpoint is `GET /api/public/config/environment`. It returns only the canonical environment, production flag, display text, explicit isolation assertion, application version, short build identifier, and deployment timestamp. It does not return host names, IP addresses, database names, connection strings, storage paths, integration endpoints, credentials, or secrets.

The test VPS deploy script writes the application stage and release metadata from the verified immutable release. Its post deployment smoke test requires:

- environment is exactly `Test`;
- `isProduction` is false;
- configuration is valid;
- the short build ID matches the deployed commit;
- the response contains no sensitive configuration field names.

## UI behavior

Production remains visually quiet:

- no top warning banner;
- no large login badge;
- the account sidebar and System Information page show a subtle Production label;
- browser title is `RHEMA-ERP`.

Non-production and Unknown environments show:

- a persistent compact banner in the authenticated shell;
- a text badge before sign in in both Light Corporate and Dark Premium login designs;
- a compact badge in the authenticated header;
- environment details in the account sidebar;
- environment context in destructive confirmation dialogs;
- an environment suffix in the browser title;
- safe release identity under Administration > System > System Information.

The environment name is always text. Color is supplementary.

## Required deployment variables

Every deployed environment must set these runtime values explicitly:

| Variable | Required value |
|---|---|
| `Application__Environment` | One of `Production`, `Test`, `UAT`, `Staging`, `Development` |
| `Application__DataIsolationConfirmed` | `true` only after database, storage, messaging, and integrations are verified separate from Production; otherwise `false` |
| `Application__Version` | Release/version identifier generated by deployment |
| `Application__BuildId` | Safe short commit or build identifier |
| `Application__DeployedAtUtc` | ISO 8601 UTC deployment timestamp |

Do not set `Application__DataIsolationConfirmed=true` from naming convention, URL, or assumption.

## Database and integration isolation audit

Repository evidence confirms:

- local Development uses a local SQL Server database and disables configured host SMS providers;
- packaged API artifacts exclude `appsettings*.json` and `.env*`, so runtime secrets are not bundled into immutable release artifacts;
- the Windows VPS keeps protected API configuration in its service configuration and preserves it across releases;
- the Test workflow and release manifest identify the release as Test;
- frontend code does not infer environment from hostname or port.

Repository evidence cannot confirm that Test/UAT/Production use distinct databases, storage roots, email/SMS providers, payment/banking systems, webhooks, or other external accounts because those protected runtime values intentionally live outside source control. No confirmed Production resource sharing was found in repository configuration, but separation is **unverified** for deployed protected configuration.

Until infrastructure owners compare the protected targets, non-production deployments must keep `Application__DataIsolationConfirmed=false`. The UI then states that isolation has not been confirmed and does not claim that changes cannot affect Production.

Before confirming isolation, compare without recording credentials:

1. database server identity and database/catalog identity;
2. file storage provider and storage account/root identity;
3. effective tenant email and SMS provider modes, recipient overrides, sandbox settings, and allowlists;
4. payment, banking, Microsoft 365, document signing, GIS, public portal, webhook, and other external integration account/mode identifiers;
5. background job and notification routing targets.

Any non-production deployment pointing to a Production database or irreversible Production integration is a critical release blocker.

## Operational checks

After each deployment:

1. request `/api/public/config/environment`;
2. verify the stage and short build ID against the release manifest;
3. open the login page and confirm the expected badge for non-production;
4. sign in and confirm the persistent banner and account sidebar context;
5. confirm Production has no warning banner;
6. leave isolation unconfirmed until protected database/storage/integration targets have been compared.
