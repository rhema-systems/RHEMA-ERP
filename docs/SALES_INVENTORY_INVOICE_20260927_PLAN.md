# Requirement 13: inventory sales through canonical customer invoices

## Verified gap

`SalesOrderService.GenerateInvoiceAsync` throws `NotImplementedException`; its controller returns HTTP 501. The order detail has no invoice-generation action. Delivery confirmation sets `IsStockDeducted` while its actual deduction remains a TODO. These flags are not stock-ledger evidence. Finance AR already owns inventory issue valuation, customer invoice workflow and AR/revenue/tax/COGS/inventory posting. Its public creation DTO currently cannot carry inventory identities, and there is no AR distribution-preview endpoint.

## Approved implementation boundary

Use the existing Sales order and canonical Finance invoice. Reserve Finance producer route 79 (`SalesOrderCustomerInvoice`); route 78 remains Inventory auction. Reuse `SalesOrder.InvoiceId`, unique per tenant and non-null invoice, with invoice line IDs matching immutable source-order line IDs. No second invoice table, stock deduction engine or independently calculated posting journal.

- A Sales-owned API adapter creates one whole-order draft invoice under a serializable transaction and order lock. Only an approved/confirmed standard order is eligible; tenant, active customer role/profile, item, warehouse/bin, lot/serial, account and tax validation remain authoritative. Existing links replay the same invoice; contradictory requests or historical partially invoiced lines fail clearly. The source order and commercial/tracking lines become immutable once linked.
- The new generation request carries invoice date, optional due date and selected exchange-rate identity, row version and idempotency key. Source quantities, prices, discounts, customer, accounts and inventory identities come from the retained order, never an arbitrary invoice payload. Freight requires an explicit configured revenue account/tax mapping; do not silently omit or guess charges.
- New trusted inventory identity fields on the canonical create DTO are accepted only through route 79 and validated against the source guard. Manual AR cannot spoof the producer route. Submit/post revalidate the entire linked order/invoice relationship. Generated documents cannot be manually edited, deleted or voided independently of their source lifecycle.
- Sales endpoints require existing explicit AR create/send/post permissions for the corresponding financial operations, plus the existing Sales read boundary and tenant scope. No permissions or roles are silently granted. Invoice submission uses the canonical workflow; posting remains an explicit authorized action.
- Sales detail exposes Generate/View Invoice and the linked invoice's Submit/Post actions. The invoice opens under a Sales-owned route so Finance's manually entered invoice UI remains independently owned. Distribution is read-only, uses the canonical Finance posting builder and a read-only valuation estimate, and identifies estimated inventory cost before posting. It never calls `ProcessIssueAsync` for preview.
- Actual posting invokes the existing canonical invoice service exactly once. Delivery confirmation remains fulfillment-only; it must not claim stock deduction without the linked posted invoice/ledger evidence or introduce another inventory issue. Posting replay cannot deduct again.

## Acceptance gates

Focused tests must cover same-tenant approved source, cross-tenant/permission denial, source-line tampering, repeated/concurrent generation, unchanged source economics, workflow gates, inventory-cost preview without mutation, balanced canonical posting, repeat-post idempotency and delivery without a second deduction. Additive migration must preserve historical order/invoice links and fail clearly on inconsistent duplicate links. Final acceptance requires real Sales UI creation and distribution plus stock ledger and balanced journal evidence; hiding the Disposal Sale option alone does not complete requirement 13.
