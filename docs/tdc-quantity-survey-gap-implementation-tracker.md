## Delivery Rule

A slice may be marked `Done` only when all applicable parts are complete:

1. Backend domain model and business rules.
2. Database migration and data backfill.
3. API endpoints and authorization.
4. Frontend routes, controls, validation, and status visibility.
5. Workflow, notifications, documents, audit events, and reports where required.
6. Automated tests for happy paths, hard stops, overrides, tenant isolation, and direct API attempts.
7. Migration applied to the test database.
8. Browser/API smoke verification.
9. Tracker evidence updated with commands, routes, and test results.

No requirement is complete merely because a field, page, or generic project-commercial record exists. TDC requires enforced QS behavior from design/site measurement through approval, valuation, certification, payment, reporting, and final account.

### Mandatory Delivery-Efficiency Gate

Quality, security, tenant isolation, SQL integrity, and acceptance evidence must not be skipped to save time. The following execution controls are nevertheless mandatory for every QS task so that verification remains proportionate and does not become the delivery bottleneck:

1. Define the smallest affected backend, database, API, frontend, and acceptance surfaces before running commands. Do not run a solution-wide build when a focused project build proves the changed boundary.
2. Run one bounded focused build for each affected compile boundary. Reuse that successful output with `--no-build` and `--no-restore`; do not rerun an unchanged successful build.
3. Run one focused automated-test pass for the changed rules, API, migration, and frontend journey. Add or rerun only the specific failing test after a correction, then run the focused affected set once for final confirmation.
4. Apply each migration once to the configured test database, then use direct SQL metadata and lifecycle probes for constraints, triggers, indexes, tenant isolation, idempotency, and retry behavior. Do not repeatedly scaffold or rebuild the full EF model after the scoped migration has passed.
5. Run one authenticated API/browser acceptance journey after the implementation and database are stable. A repeated smoke is required only when a later code, configuration, migration, or deployed-artifact change can affect that journey.
6. Do not run concurrent heavy .NET, EF, Next.js, or test commands against shared output folders. File-lock failures caused by overlapping commands do not justify repeating the entire gate sequence.
7. Time-box investigation of a silent or slow command. Inspect it once for active CPU/output and dependency contention; if it is not demonstrably progressing, stop it, capture the boundary, and use a narrower command or report the concrete blocker. Never leave duplicate compilers, development servers, browsers, or deployment processes running.
8. Record the command and result once in the tracker. Documentation-only edits after a successful gate require `git diff --check`, not another backend/frontend build.

This efficiency gate controls how the Delivery Rule is proven; it does not reduce the Delivery Rule. A task remains `In progress` when a required runtime acceptance gate lacks representative source data, but implementation work must move to the next safe task instead of repeatedly rerunning unchanged checks.
