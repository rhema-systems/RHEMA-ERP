# Tender Playwright lifecycle coverage matrix

## Purpose and acceptance boundary

This matrix defines the browser, API, and SQL Server evidence required before the TDC tender lifecycle may be reported as end-to-end tested. It is derived from the current frontend routes, controllers, services, permission registry, and EF entities. It is not evidence that the lifecycle has already passed.

The acceptance suite must:

- run against a disposable or explicitly designated SQL Server acceptance tenant;
- use the real application and APIs without `page.route(...).fulfill(...)` or mocked procurement responses;
- use fresh, uniquely named records for every run and retain their generated IDs as test state;
- authenticate each distinct actor separately and preserve maker/checker segregation;
- assert the visible browser result, the HTTP response, and the persisted tenant-scoped database state after each transition;
- capture traces, screenshots, response bodies, correlation IDs, and relevant SQL assertions on failure;
- repeat final mutations to prove idempotency or a controlled conflict, rather than duplicate data;
- execute the negative and cross-tenant cases in a separate data branch so they cannot corrupt the positive journey.

## Deterministic actors and configuration

Use dedicated acceptance users; do not use a generic administrator as every actor.

| Actor | Required Security role or permission | Purpose |
| --- | --- | --- |
| Requester | `TDC_REQUISITIONER` / `procurement.requisition.create` | Creates the source requisition. |
| PR approver | `TDC_USER_DEPARTMENT_HEAD`, `TDC_FINANCE_REVIEWER`, or the configured independent workflow approver / `procurement.requisition.approve` | Approves the PR and proves maker/checker separation. |
| Tender administrator | `TDC_PROCUREMENT_OFFICER`, `TDC_SENIOR_PROCUREMENT_OFFICER`, or `TDC_HEAD_OF_PROCUREMENT` / `procurement.sourcing.manage` and `procurement.tender.administer` | Creates the sourcing case and administers the tender. |
| Fee verifier | A distinct user with `procurement.tender.payment.verify` (currently included in Procurement Officer and Senior Procurement Officer) | Verifies or rejects manual fee claims and creates Finance posting lineage. |
| Evaluator A/B/C | Three different `TDC_EVALUATOR` users / `procurement.tender.evaluate` | Form the evaluation committee and submit independent scores. |
| Tender approver | An independently assigned `TDC_HEAD_OF_PROCUREMENT`, `TDC_MANAGING_DIRECTOR`, `TDC_BOARD_APPROVER`, `TDC_ETC_MEMBER`, or `TDC_CENTRAL_REVIEW_MEMBER` / `procurement.tender.approve` | Approves tender and award decisions. |
| Contract maker | `TDC_PROCUREMENT_OFFICER`, `TDC_SENIOR_PROCUREMENT_OFFICER`, or `TDC_HEAD_OF_PROCUREMENT` / `procurement.contract.manage` | Creates a contract from an approved award. |
| Contract approver | A distinct user with `procurement.contract.approve` | Activates, completes, terminates, or approves contract amendments. |
| PO maker | `TDC_PROCUREMENT_OFFICER` or `TDC_SENIOR_PROCUREMENT_OFFICER` / `procurement.purchase-order.create` | Creates a PO from an approved award. |
| Supplier A | External user linked to active eligible supplier A and the acceptance tenant | Primary positive bidder. |
| Supplier B | External user linked to active eligible supplier B and the acceptance tenant | Competing bidder and ranking evidence. |
| Supplier blocked | External user linked to a suspended, ineligible, uninvited, or other-tenant supplier | Negative access and eligibility cases. |
| Unauthorized internal | Authenticated user without the relevant procurement permission | 403 and hidden-action assertions. |

Required data/configuration for the positive journey:

- one published and effective procurement policy covering category `Goods`, the selected amount, currency, authority route, and tender method;
- one approved procurement-plan item and effective budget with enough remaining value for the PR and final award;
- one approved PR with at least two lines, an exact currency, complete plan/budget/authority lineage, and no prior active sourcing case;
- one active `Goods` + `ITB` evaluation template whose criteria total and thresholds are valid;
- a locked sourcing case whose value and currency exactly match the PR/tender;
- future dates computed from server UTC: submission deadline at least 30 minutes ahead and opening at least 5 minutes after the deadline;
- supplier A and B active, approved, assigned to `Goods`, not suspended, and carrying every effective eligibility document through at least the configured minimum-validity window;
- supplier A and B each linked to a different active external portal user;
- three active evaluator users plus a published/effective evaluation committee template and safe DMS evidence references;
- for the fee branch, a mandatory manual `TenderFee` in the tenant functional currency, an active direct-posting non-control asset receiving account, and a different active direct-posting non-control revenue account;
- required tender/bid documents represented by safe central DMS references;
- workflow definitions and independent assignees for tender, award, contract, and PO decisions used by the selected amount band;
- use a run key such as `E2E-TND-<UTC timestamp>` in titles, references, evidence, signatures, payment transaction IDs, and idempotency keys. Never rely on fixed database GUIDs.

## Mandatory SQL verification pattern

The Playwright worker should call a dedicated acceptance verifier (or a restricted read-only SQL helper outside the browser bundle) after each successful transition. At minimum, every assertion must include `TenantId`, `IsDeleted`, primary ID, status, source foreign keys, actor ID, and timestamp. Multi-table transitions must be verified in one read-consistent query.

Core tables involved are:

- `PurchaseRequisitions`, approved budget/authority/workflow tables, and `ProcurementRequisitionSourcingReleases`;
- `ProcurementSourcingCases`, `ProcurementSourcingCaseLots`, `ProcurementSourcingCaseLotItems`, and `ProcurementSourcingCaseSourceRequests`;
- `Tenders`, `TenderLots`, `TenderItems`, `TenderDocuments`, `TenderInvitations`, `TenderFees`, `TenderEvaluators`, `TenderRevisions`, and `TenderViewLogs`;
- `TenderAssignments`, `TenderBids`, `TenderBidLots`, `TenderBidItems`, `TenderBidDocuments`, and `TenderPayments`;
- `ProcurementEvaluationCommitteeControls`, role requirements, appointments, conflict declarations, meetings, attendance records, score sheets, and score recalls;
- `TenderEvaluations`, `TenderAwards`, award verification/readiness/control records, bidder communications, and audit/exception history;
- `FinancePostingEvents`, journal-entry header/lines, budget reservation/commitment tables, `Contracts`, `ContractAmendments`, purchase orders, and immutable source snapshots.

SQL verification must prove both presence and uniqueness. For example, payment verification must find one posting event and one balanced journal, sourcing start must find one current release/case, evaluation submit must find one locked sheet per evaluator/bid/idempotency key, and award conversion must find one contract or PO for the chosen route.

## Current Playwright gaps

The current `e2e-tests/tests/p2p.spec.ts` is navigation smoke only. It logs in as one `admin` user, opens Purchase Orders, Purchase Receipts, Vendor Invoices, and Vendor Payments, and only asserts that the body does not contain `Application error`.

No current Playwright spec was found that performs the tender lifecycle above. Specifically, current Playwright coverage does not prove:

- approved PR sourcing readiness, automatic release, locked sourcing case, or immutable tender lineage;
- tender wizard save/reopen fidelity for evaluation template, lots, items, invitations, fees, and documents;
- tender workflow submission/approval, publication controls, deadline/opening rules, or invitation status transitions;
- supplier association scopes, declaration, payment evidence/verification, Finance journal link, or sealed-bid payment admission behavior;
- bid lot/item/proposal/document draft persistence, second supplier competition, updated submission, withdrawal, or ownership/tenant isolation;
- formal opening, statutory controls, committee appointment/COI/activation/meeting/quorum, evaluation draft reload, locked score submission, or consolidated ranking;
- award readiness, award maker/checker approval, bidder communication, contract/PO conversion, budget commitment uniqueness, contract amendment, cancellation/termination, or retry/idempotency;
- direct unauthorized API calls and database non-mutation after each visible action;
- print/export behavior for tender-family documents.

Unit, service, controller, frontend helper, migration-guard, and mocked-request tests remain useful regression gates, but they do not satisfy this matrix. Completion requires the authenticated browser journey, real API responses, and real SQL Server assertions for the exact deployed candidate.

## Release decision

The tender lifecycle is **release-safe for manual UAT only when**:

1. TND-001 through TND-029, including TND-009A, pass on a fresh acceptance run (TND-025A and TND-025B may use separate cloned awards or separate runs).
2. Every expected 4xx response has the stable business code and readable detail specified by the server boundary; no expected rule failure surfaces as 500.
3. There are no uncaught browser errors, failed application requests, tenant leaks, duplicate immutable records, duplicate Finance postings/commitments, or stale fields after refresh.
4. The full focused backend/frontend regression set passes after the browser run.
5. The same candidate package and migration set is deployed through the guarded VPS runbook, followed by authenticated VPS smoke of the critical positive path. A localhost pass alone is not a VPS acceptance result.
