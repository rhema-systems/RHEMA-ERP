TDC ERP VPS server-side redeployment

A single procedure for updating the VPS from master, applying backend and frontend changes together, restarting the correct services, and verifying the live release.

Use this on the Windows test VPS as Administrator. The live runtime is C:\RhemaERP. Do not run Git commands in C:\RhemaERP\api or C:\RhemaERP\frontend; those folders contain the deployed application, protected settings, uploads, and logs. Run Git only in the separate ERP source clone.

1. Find and prepare the source clone

Open an elevated PowerShell window on the VPS. Set $repo to the folder containing the ERP repository’s .git folder. It must be a normal clone of the same repository, not a copy of the deployed runtime.

$repo = 'C:\Path\To\erp-system-source'
Set-Location $repo
git rev-parse --show-toplevel
git status --short
git remote -v

Continue only when git status --short produces no output. If it lists files, stop: server-only edits must be preserved and reviewed before any pull. Do not use git reset --hard, git clean, or overwrite the runtime folders.

2. Pull the merged changes from master

The VPS should follow the already-merged master branch. A manual merge is normally unnecessary. Use a fast-forward-only pull so Git refuses an unexpected VPS-only branch or commit.

Set-Location $repo
git fetch --prune origin
git log --oneline HEAD..origin/master
git diff --name-only HEAD..origin/master -- src/ErpSystem.Data/Migrations
git pull --ff-only origin master
git status -sb
git log -1 --oneline
If Git says it cannot fast-forward, stop. Do not run a blind merge. That means the VPS clone has commits that are not on origin/master. Inspect them with git log --oneline origin/master..HEAD, decide whether they belong in a pull request, then return the VPS source clone to the approved release branch.

The migration comparison is deliberate. It tells you whether this release changes the database before services are touched.

Baseline cutover decision

Do not deploy the current baseline to a VPS database with retained data and older migration history. The disposable-development baseline creates a fresh schema; it is not a data-preserving upgrade path. The deployment dry run intentionally stops in this condition.

If the VPS database is empty or the owner has explicitly declared every record disposable, use the separately reviewed guarded reset procedure and its backup/evidence requirements. If the VPS data must be retained or ownership is uncertain, keep the previous compatible code/database pair running. A data-preserving migration or export/import cutover must be designed and reviewed separately before this branch can be deployed.

Disposable test-data reset

Use this procedure only after the database owner has explicitly declared the VPS RhemaERP data disposable. It makes a verified COPY_ONLY SQL backup, records immutable reset evidence outside the repository, then drops and recreates the database. It does not run against a remote SQL server, a different database name, an unknown Git state, or enabled Finance accounting producers.

Run this before the normal deployment gate. Stop the API and frontend so neither service reconnects while the reset owns the database. Do not delete the backup or evidence directory if the reset fails; the script deliberately does not retry or auto-restore.
Set-Location $repo
Stop-Service RhemaERPFrontend
Stop-Service RhemaERPAPI

# Read the existing protected SQL setting into this PowerShell process only.
# The command does not display the connection string.
$parameters = Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\RhemaERPAPI\Parameters'
$allEntries = @(@($parameters.AppEnvironment) + @($parameters.AppEnvironmentExtra)) |
  ForEach-Object { [string]$_ }
$connectionEntry = @($allEntries | Where-Object {
  $_ -like 'ConnectionStrings__DefaultConnection=*'
} | Select-Object -Last 1)[0]
if ([string]::IsNullOrWhiteSpace($connectionEntry)) {
  throw 'The API NSSM configuration has no protected SQL connection setting.'
}
$env:RHEMA_GL_DISPOSABLE_DEVELOPMENT_CONNECTION =
  $connectionEntry.Substring('ConnectionStrings__DefaultConnection='.Length)

$env:RHEMA_GL_DISPOSABLE_DEVELOPMENT_RESET_ATTESTATION =
  'I_ATTEST_RHEMAERP_DEVELOPMENT_DATA_IS_DISPOSABLE'
$env:RHEMA_GL_REVIEWED_COMMIT = (git rev-parse HEAD).Trim()
$env:RHEMA_GL_REVIEWED_TREE = (git rev-parse 'HEAD^{tree}').Trim()
$env:Finance__AccountingEvents__Enabled = 'false'
$env:Finance__ProducerIntents__Enabled = 'false'
$env:Finance__ProducerIntentGroups__Enabled = 'false'
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$evidence = "C:\RhemaERP\backups\disposable-reset-$stamp"

powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File .\scripts\finance\Invoke-GlCutoverRehearsal.ps1 `
  -Mode ResetDisposableDevelopment `
  -ConfirmDisposableDevelopmentReset `
  -EvidenceDirectory $evidence

Continue only when the reset reports a verified backup, exact final migration history, seed and invariant checks, and DBCC CHECKDB. Keep $evidence and its SQL backup. Then clear only the process-scoped sensitive variables, start the services, and use the normal dry run and deployment in the next section.

Remove-Item Env:RHEMA_GL_DISPOSABLE_DEVELOPMENT_CONNECTION -ErrorAction SilentlyContinue
Remove-Item Env:RHEMA_GL_DISPOSABLE_DEVELOPMENT_RESET_ATTESTATION -ErrorAction SilentlyContinue
Start-Service RhemaERPAPI
Start-Service RhemaERPFrontend

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Deploy-RhemaVps.ps1 -Environment Test -LocalVps -DryRun
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Deploy-RhemaVps.ps1 -Environment Test -LocalVps

3. Run the deployment gate and build a production release

The repository deployment script is the supported release mechanism. Its -LocalVps mode runs entirely on the VPS: no SSH connection and no SSH key are used. It verifies the exact origin/master commit, checks database migration parity, creates application and SQL backups, publishes a self-contained API, builds a clean production frontend, applies both packages, restarts services, and records release evidence.

Set-Location $repo
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Deploy-RhemaVps.ps1 -Environment Test -LocalVps -DryRun

Read the dry-run result first. It must pass preflight checks. Then run the release:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Deploy-RhemaVps.ps1 -Environment Test -LocalVps

For a new commit, omit -ReuseVerifiedArtifacts so the VPS builds fresh packages. The normal remote-workstation mode still uses SSH; use -LocalVps only when you are signed in directly to this VPS.

Frontend rule: the VPS must run a production build through npm run build and the RhemaERPFrontend service runs the production server. Never use npm run dev on the VPS. The build embeds the public API URL https://149.102.145.190:8443/api; changing an environment file after the build does not change compiled browser code.

If you need to verify the intended production frontend variables before building, they are:

$env:NODE_ENV = 'production'
$env:NEXT_PUBLIC_API_URL = 'https://149.102.145.190:8443/api'
$env:API_URL = 'https://149.102.145.190:8443/api'
$env:NEXTAUTH_URL = 'https://149.102.145.190:8443'
$env:NEXT_TELEMETRY_DISABLED = '1'

4. What the release changes and preserves

ComponentDeployment behaviour
APIPublished self-contained to a staged package, then copied to C:\RhemaERP\api. Protected configuration, uploads, logs, and secure file storage are preserved.
DatabaseAn application snapshot and SQL COPY_ONLY, compressed, checksummed backup are created and verified before services change. Startup applies migrations; allow several minutes for this stage.
FrontendA complete new .next, public, runtime node_modules, server.js, and package.json set replaces the old build while the frontend service is stopped.
ProxyRhemaERPHTTPSIPProxy normally remains running. Restart it only when its configuration changed. It serves HTTPS on port 8443 and routes /api and health paths to the API.

Do not mirror-delete API folders, deploy a frontend one folder at a time, or copy new files into a running .next directory. Those actions can remove runtime uploads or create stale/missing JavaScript and CSS chunks.

5. Service restart and local checks

The deployment script restarts the API and frontend itself. If you need to restart them after a completed deployment or after a controlled recovery, use:

Restart-Service RhemaERPAPI
Restart-Service RhemaERPFrontend
Get-Service RhemaERPAPI,RhemaERPFrontend,RhemaERPHTTPSIPProxy

Invoke-WebRequest 'http://127.0.0.1:5000/health' -UseBasicParsing
Invoke-WebRequest 'http://127.0.0.1:3001/login' -UseBasicParsing

Expected result: all three services are Running, the local API health endpoint is healthy, and local frontend login returns HTTP 200. The API may take several minutes while startup migrations complete; do not repeatedly restart it during that window.

If the HTTPS proxy is missing or stopped: run the following single command from this repository in an elevated Windows PowerShell window. It restores the proxy script, securely installs the pinned ACME client when missing, obtains the IP certificate through the configured ACME challenge, corrects the NSSM service and verifies port 8443.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\vps\Repair-RhemaVpsHttpsProxy.ps1

Continue only after the command reports HTTPS_PROXY_REPAIR|PASS. Then rerun the normal -LocalVps -DryRun check.

6. Verify the public deployment

$base = 'https://149.102.145.190:8443'
Invoke-WebRequest "$base/health" -SkipCertificateCheck -UseBasicParsing
Invoke-WebRequest "$base/health/ready" -SkipCertificateCheck -UseBasicParsing
Invoke-WebRequest "$base/health/live" -SkipCertificateCheck -UseBasicParsing
Invoke-WebRequest "$base/api/tenant" -SkipCertificateCheck -UseBasicParsing
Invoke-WebRequest "$base/login" -SkipCertificateCheck -UseBasicParsing
Invoke-WebRequest "$base/sw.js" -SkipCertificateCheck -UseBasicParsing
Get-Service RhemaERPAPI,RhemaERPFrontend,RhemaERPHTTPSIPProxy

Confirm /health and /health/ready are healthy, /api/tenant and /login return HTTP 200, and the service worker has the new cache version. Open the live site at https://149.102.145.190:8443, sign in, and test the affected feature.

Release complete only after: the services are running, migrations completed, local and public health are healthy, login works, and the changed browser journey succeeds without 5xx responses or missing static assets.

Browsers must use HTTPS port 8443. Do not expose or browse directly to public port 5000; it is API loopback-only.

7. If the deployment fails

Do not repeatedly rerun the full release. Review the failed stage and the evidence under artifacts\vps-releases and C:\RhemaERP\logs. The deployment process keeps a commit-keyed application snapshot under C:\RhemaERP\backups and verifies the SQL backup before applying changes. Restore application files from the matching snapshot only when needed; restore the SQL backup only when a migration or data rollback is explicitly required.

For the full package layout, backup, rollback, and browser smoke details, use the repository runbook: VPS_DEPLOYMENT_RUNBOOK.md.
