REQUIREMENT 1 — ACTUAL QUANTITY RECEIVED DURING ACKNOWLEDGEMENT

Currently, when the requester acknowledges receipt of items issued through an Inventory Requisition, the system does not provide a proper receiving grid where the requester can confirm the actual quantities physically received.

Modify the acknowledgement process.

Before the requester clicks the final "Acknowledge" button, display an item grid similar to the existing Inter-Store Transfer receipt screen.

The grid should show relevant information including:

- Item Code
- Item Description
- Quantity Requested
- Quantity Issued
- Quantity Previously Received, if applicable
- Outstanding Quantity, if applicable
- Actual Quantity Received
- Unit of Measure
- Issuing Store/Warehouse
- Relevant reference/document number

The requester must be able to enter or confirm the Actual Quantity Received for every line before acknowledgement.

Do NOT assume that Quantity Issued automatically equals Quantity Received.

Example:

Quantity Requested = 100
Quantity Issued = 100
Actual Quantity Received = 92

The system must record 92 as received, not 100.

If partial acknowledgement is supported:

Received = 92
Outstanding = 8

The remaining quantity must remain outstanding.

Investigate and correctly handle:

- Partial receipts
- Multiple acknowledgements
- Short receipts
- Previously acknowledged quantities
- Outstanding quantities
- Over-receipt validation
- Cancelled/reversed issues where supported

Reuse the existing Inter-Store Transfer receipt implementation where practical so the two receiving experiences remain consistent.

Ensure the Inventory Movement/Ledger reflects the actual acknowledged quantity rather than an assumed quantity where the acknowledgement affects inventory records.

WORKSTREAM 2 — INTER-STORE TRANSFER
==================================================

REQUIREMENT 2 — BIN MUST NOT BE REQUIRED DURING TRANSFER REQUEST, BUT MUST BE REQUIRED DURING STOCK ISSUE

The current Inter-Store Transfer process requires the requester to select a Bin for transfer items too early in the process.

This behaviour must be changed.

The key business rule is:

THE REQUESTER SHOULD NOT SELECT THE SOURCE BIN WHEN CREATING THE INTER-STORE TRANSFER REQUEST.

The requester normally knows:

- Which item is required
- What quantity is required
- Which Store/Warehouse should supply it
- Which Store/Warehouse should receive it

However, the requester may NOT know the exact Bin in the source Store where the physical stock is located.

Bin selection belongs to the Store/Warehouse officer who is actually issuing the stock.

--------------------------------------------------
TRANSFER REQUEST STAGE
--------------------------------------------------

When creating an Inter-Store Transfer Request:

The requester should select:

- Source Store/Warehouse
- Destination Store/Warehouse
- Item
- Requested Quantity
- Unit of Measure
- Other existing required request information

The requester must NOT be required to select:

- Source Bin

Do not make Source Bin mandatory in either frontend or backend validation during the REQUEST stage.

If the current data model requires a Bin ID on every transfer line, refactor the workflow/data model appropriately rather than forcing the requester to enter a meaningless placeholder bin.

A transfer request must be valid without knowing the physical source bin.

Conceptually:

Requester:

"I need 20 units of Item ABC from Main Warehouse."

NOT:

"I need 20 units of Item ABC specifically from Bin A-03-02."

The physical stock location is the responsibility of the warehouse/store issuing officer.

--------------------------------------------------
TRANSFER APPROVAL STAGE
--------------------------------------------------

If the Inter-Store Transfer requires approval, the absence of a Source Bin must NOT prevent the transfer request from moving through approval.

The requested item and quantity should be approved independently of the physical picking/bin decision.

The Bin should still remain unresolved until the actual Issue/Picking stage.

--------------------------------------------------
TRANSFER ISSUE / PICKING STAGE
--------------------------------------------------

When the approved transfer reaches the actual Stock Issue/Picking stage:

The Store/Warehouse officer MUST select the Source Bin from which the stock is physically being issued.

At this point Bin selection is required because inventory is actually about to leave a physical stock location.

The system should show the warehouse officer only valid bins for:

- The selected Source Store/Warehouse
- The selected Item
- Available stock
- Relevant Unit of Measure
- Any other existing inventory restrictions

The warehouse officer should be able to see useful information such as:

- Bin
- Quantity Available
- Quantity Reserved, where applicable
- Quantity Available to Issue
- Lot/Batch where applicable
- Serial information where applicable

The selected Source Bin must have sufficient available inventory for the quantity being issued unless the ERP explicitly supports splitting across bins.

--------------------------------------------------
MULTIPLE SOURCE BINS
--------------------------------------------------

If the requested quantity is available across multiple bins, support the existing ERP's normal inventory picking behaviour.

For example:

Transfer Request Quantity = 100

Available stock:

Bin A = 60
Bin B = 40

The warehouse officer should be able to issue:

Bin A = 60
Bin B = 40

Total Issued = 100

Do not force the requester to predict this bin allocation when creating the request.

If the ERP already has picking/allocation functionality, reuse it.

--------------------------------------------------
PARTIAL ISSUE
--------------------------------------------------

Support partial issue where the existing business process permits it.

Example:

Requested Quantity = 100
Currently Available = 80

Issued = 80
Outstanding = 20

The system must maintain the outstanding transfer quantity correctly.

The remaining 20 should not disappear merely because part of the transfer has been issued.

--------------------------------------------------
DESTINATION BIN
--------------------------------------------------

Do not confuse Source Bin selection with Destination Bin selection.

The Source Bin is selected during Issue/Picking by the issuing Store/Warehouse officer.

For Destination Bin handling during receipt:

Inspect the existing warehouse/bin configuration and retain the appropriate receiving behaviour.

If the destination warehouse requires Bin-level receiving, the receiving officer may select the Destination Bin at the actual Receipt stage.

Do not require the original requester to know either the Source Bin or Destination Bin when submitting the transfer request unless there is an explicit configured business reason.

--------------------------------------------------
VALIDATION RULE
--------------------------------------------------

The validation must therefore be stage-aware:

TRANSFER REQUEST:

Source Bin = NOT REQUIRED

TRANSFER APPROVAL:

Source Bin = NOT REQUIRED

TRANSFER ISSUE / PICKING:

Source Bin = REQUIRED

TRANSFER RECEIPT:

Destination Bin = based on the existing destination warehouse/bin configuration and receiving workflow.

Update:

- Frontend validation
- Backend validation
- DTOs
- Commands
- Domain validation
- Database assumptions
- APIs
- Approval workflow
- Issue workflow

accordingly.

Do not solve this by making Bin nullable everywhere without enforcing it at the Issue stage.

The objective is to require the Bin at the correct point in the business process.

REQUIREMENT 4 — SYSTEM-MANAGED IN-TRANSIT LOCATION

Create a system-managed virtual In-Transit inventory location.

The objective is to properly represent stock that has left the Source Store but has not yet been received by the Destination Store.

The required transfer flow is:

Transfer Request
→ Approval, where applicable
→ Source Bin Selection / Issue
→ In-Transit Location
→ Destination Receipt
→ Destination Store/Bin

When an Inter-Store Transfer is actually issued:

1. Stock leaves the selected Source Bin/Source Store.
2. The same quantity automatically enters the In-Transit Location.
3. That stock remains in transit until the receiving Store confirms receipt.
4. When received, stock leaves In-Transit and enters the Destination Store.
5. Any quantity not yet received must remain in In-Transit.

IMPORTANT:

Creating or approving a Transfer Request must NOT move inventory.

Inventory enters In-Transit only when stock has actually been issued/shipped.

Example:

Requested Quantity = 100

At request stage:

Source Store inventory = unchanged
In-Transit = unchanged
Destination Store = unchanged

After warehouse officer issues 100:

Source Store = -100
In-Transit = +100

Destination receives 80:

In-Transit = -80
Destination Store = +80

Remaining In-Transit = 20

The outstanding 20 must continue to show in reports until eventually received, returned, cancelled, lost, or otherwise resolved through an authorized business process.

--------------------------------------------------
IN-TRANSIT LOCATION RULES
--------------------------------------------------

The In-Transit Location should:

- Be system-managed
- Hold all and only stock currently in transit
- Appear in Inventory Ledger and relevant inventory reports
- Not normally be available for ordinary stock issues
- Not normally be manually selected as an operational Store
- Not be manually manipulated by ordinary users
- Automatically receive quantities from actual Transfer Issue/Shipment
- Automatically release quantities during Transfer Receipt
- Support partial receipts
- Support partial issues
- Support multiple open transfers simultaneously
- Maintain traceability to the originating Transfer

The system must not lose traceability simply because multiple transfers use one virtual In-Transit Location.

Each In-Transit quantity must remain associated with its originating transfer.

--------------------------------------------------
VEHICLE / TRUCK / COURIER AS TEMPORARY TRANSIT CONTAINER
--------------------------------------------------

The physical Carrier/Vehicle/Truck/Courier used to transport stock should conceptually function like a temporary transit container/bin within the In-Transit process.

The business objective is to know not only:

"100 units are in transit"

but, where transportation information exists:

"100 units are in transit under Transfer X using Carrier/Vehicle Y."

Do not force this into the existing Warehouse Bin table if doing so conflicts with the domain architecture.

Inspect how:

- Vehicles
- Carriers
- Suppliers
- Bins
- Locations
- Stores
- Transfers

are currently modeled.

Choose the cleanest architecture-compatible implementation.

A conceptual structure may be:

In-Transit Location
    ↓
Transfer
    ↓
Carrier / Vehicle / Courier
    ↓
Items / Quantities In Transit

The Carrier/Vehicle information is primarily for traceability.

The authoritative inventory balance must remain represented correctly in the In-Transit location.

--------------------------------------------------
REPORTING
--------------------------------------------------

In-Transit quantities must appear in appropriate reports.

At minimum users should be able to determine:

- Item
- Transfer Number
- Source Store
- Destination Store
- Source Bin(s)
- Quantity Requested
- Quantity Issued
- Quantity Received
- Quantity Still In Transit
- Shipment Date
- Carrier
- Vehicle/reference where available
- Number of days in transit where practical

Do not calculate In-Transit stock using only Transfer Status if proper inventory movement records exist.

Use the Inventory Movement/Ledger as the authoritative quantity source where appropriate.

WORKSTREAM 4 — STOCK COUNT INVESTIGATION AND RECOUNT
==================================================

REQUIREMENT 6 — MARK COUNT ITEMS FOR INVESTIGATION / RECOUNT

Add a checkbox/action per Stock Count item similar to:

"Require Investigation / Recount"

The flag applies to an individual Count Sheet line.

A Stock Count may therefore contain:

- Passed items
- Items requiring investigation/recount

Some lines requiring recount must NOT block all passed items from continuing through the normal Stock Count approval workflow.

--------------------------------------------------
EXPECTED WORKFLOW
--------------------------------------------------

Example:

Item A — Passed
Item B — Passed
Item C — Recount Required
Item D — Passed
Item E — Recount Required

The original Stock Count can continue through its configured approval workflow.

Passed entries:

A
B
D

continue through approval and eventually become eligible for Stock Adjustment.

Recount entries:

C
E

must be excluded from the passed-item adjustment processing for that count cycle.

They must be returned to the assigned Counters for investigation/recount.

--------------------------------------------------
GRID BEHAVIOUR
--------------------------------------------------

For users processing the original count:

Recount-required lines should be hidden by default from the normal passed-item grid.

Provide a button/toggle such as:

"Show Recount / Investigation Items"

Authorized users should be able to display the excluded lines when required.

Do not delete or detach these records.

They remain linked to the original Count Sheet.

--------------------------------------------------
RECOUNT NOTIFICATION
--------------------------------------------------

When items are marked for recount, notify the assigned Counters.

The notification should indicate:

- Stock Count
- Count Sheet
- Items requiring recount
- Store/Warehouse
- Reason/comment where provided

The Counters should return to the same overall Stock Count context.

However, only the lines requiring recount should be available for recount data entry.

Previously passed lines should not appear as editable recount lines.

--------------------------------------------------
ADDENDUM COUNT SHEET
--------------------------------------------------

When Counters complete the recount and submit:

Create a NEW Count Sheet Addendum containing only the recounted items.

The Addendum must:

- Link to the original Stock Count
- Link to the original Count Sheet
- Identify itself as a Recount/Addendum
- Contain only the items requiring recount
- Maintain recount attempt/version information
- Preserve original count values
- Store new recount values
- Begin the same configured approval workflow again

Do NOT overwrite the original submitted Count Sheet.

Conceptually:

Stock Count
   │
   ├── Original Count Sheet
   │       ├── Passed lines → approval → adjustment
   │       └── Recount lines
   │
   └── Recount Addendum #1
           ├── Recounted lines
           ├── approval workflow
           └── adjustment after approval

If an Addendum itself contains lines requiring another recount, support another recount cycle.

Example:

Original Count Sheet
→ Recount Addendum 1
→ Recount Addendum 2

Maintain the complete history.

--------------------------------------------------
STOCK ADJUSTMENT
--------------------------------------------------

Passed original items may proceed to Stock Adjustment once properly approved.

Recount items must NOT be adjusted using the rejected/original value.

They should only be adjusted using the finally approved recount/addendum result.

Prevent the same difference from being adjusted twice.

Add a column to:

- Count Sheet item grid
- Uploaded Count Sheet / Items grid

"Defective Quantity"

or equivalent existing terminology.

Also allow a comment/remark against the defective quantity.

Example:

System Quantity = 100
Physical Count = 100
Defective Quantity = 5

The fact that 5 units are defective is supplementary information.

CRITICAL RULE:

Defective Quantity MUST NOT affect Stock Count variance calculations.

- Physical Count
- Counted Quantity
- Variance
- Stock Adjustment Quantity

Example:

System Qty = 100
Physical Count = 100
Defective Qty = 5

NOT:

Variance = -5

- Defective Location

That later movement is separate from the Stock Count adjustment.

--------------------------------------------------
VALIDATION
--------------------------------------------------

At minimum:

Defective Quantity >= 0

and normally:

Defective Quantity <= Physical Count

unless the existing inventory model requires another valid rule.

Allow a comment explaining the defect.

Maintain audit history.

REQUIREMENT 8 — SUPPLIER INVOICE COST DIFFERENT FROM ORIGINAL GRN COST

When processing a Supplier Invoice, the Supplier Invoice item cost may differ from the cost recorded on the original GRN when goods were received.

The ERP must support two company-policy approaches:

1. Revalue Inventory
2. Post the difference to Purchase Price Variance

Configure this company policy under Procurement Settings.

The setting should conceptually provide:

Purchase Price Difference Handling:

- Revalue Inventory
- Post to Purchase Price Variance

Reuse an existing equivalent setting if one exists.

--------------------------------------------------
EXAMPLE
--------------------------------------------------

Original GRN:

Quantity = 100
GRN Unit Cost = GHS 10
Original Value = GHS 1,000

Supplier Invoice:

Quantity = 100
Invoice Unit Cost = GHS 11
Invoice Value = GHS 1,100

Difference = GHS 100

Handling depends on Procurement Settings.

--------------------------------------------------
OPTION A — REVALUE INVENTORY
--------------------------------------------------

If company policy is:

Revalue Inventory

follow the existing inventory costing/revaluation architecture.

Do NOT alter the historical original GRN cost.

The original GRN remains an accurate historical receipt document.

Create the appropriate cost-adjustment/revaluation transaction.

Consider stock already:

- Issued
- Consumed
- Transferred
- Sold
- Otherwise removed from inventory

Do not blindly revalue quantities no longer on hand.

Use the ERP's configured costing method and existing cost-adjustment rules.

--------------------------------------------------
OPTION B — PURCHASE PRICE VARIANCE
--------------------------------------------------

If company policy is:

Post to Purchase Price Variance

post the difference to the Item's configured Purchase Price Variance GL Account rather than revaluing inventory.

Use the Purchase Price Variance account configured against the Item.

If the Item does not currently support this account, determine whether it belongs in the Item Accounts tab and add it according to the ERP's existing GL account architecture.

Do not hard-code a GL account.

--------------------------------------------------
GENERAL RULES
--------------------------------------------------

Determine variance at the appropriate line level.

Handle:

- Positive variance
- Negative variance
- Partial invoice
- Multiple invoices against a GRN
- Partial quantities
- Taxes separately according to existing tax rules
- Currency/exchange-rate handling using existing architecture

Maintain traceability:

Supplier Invoice
→ Invoice Line
→ GRN Line
→ Cost Difference
→ Revaluation or PPV Journal Entry

Prevent duplicate variance processing when posting is retried.

Debit: Supplier / Accounts Payable balance

--------------------------------------------------

10 reversing Accounts Payable

subject to the existing ERP's allocation rules.
