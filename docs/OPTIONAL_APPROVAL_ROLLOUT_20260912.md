### Payment documents without an active approval process

- **Source implementation complete; deployment pending.** An inactive, non-in-flight draft payment uploads required files through `POST /api/ap/payments/{id}/evidence`, using central controlled upload and DMS storage. It does not need a fabricated workflow step.
- **No human verification:** the UI shows **Not required**, with no reviewer or Verify action. No verifier identity/date is invented. Active or already-running approvals retain their existing upload and verification controls.
- **Files are still required:** immutable payment links bind the exact tenant, payment, requirement, DMS record/version and uploaded file. Current policy, expiry, clean scan, stored-file presence and actual file hash are checked by the payment owner. Missing or changed evidence blocks completion/posting; separate configured MD/signature requirements are not waived.
- **Protected access:** payment content uses `GET /api/ap/payments/{id}/evidence/{evidenceId}/content`. Generic DMS access also requires Finance Read and the payment's exact bank Read scope before any broader DMS/admin fallback. Generic DMS cannot relabel, replace, publish or otherwise mutate payment-owned evidence.
- **No alternate download bypass:** generic DMS record/version/download routes resolve the exact payment evidence link and delegate to the same payment-owned integrity checks. They do not serve cached renditions or unchecked raw files. Payment attachments are delivered in their original format; unsupported conversion fails closed. Other DMS source types keep their existing behavior.
