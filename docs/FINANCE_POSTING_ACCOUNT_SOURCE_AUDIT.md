This is a source audit, not a claim of completed live accounting acceptance. Line references describe the inspected checkout and may move during fixes. Builds/tests are coordinated by the parent regression workstream.

## Authority and source matrix

## Confirmed defects corrected in this audit

1. **AR invoice create used obsolete partner payment terms despite capturing an approved AR profile.** It selected `customer.PaymentTermId` and parsed `customer.PaymentTerms`, allowing a saved Finance profile to appear ignored. Changed to explicit request → effective approved profile → configured customer/all default → existing 30-day fallback. Added four cases in `tests/ErpSystem.Api.Tests/Services/Finance/ArInvoicePostingMigrationTests.cs`, `CreateInvoice_ShouldUseApprovedProfileTermsOrCanonicalDefault`: stale legacy 90-day term versus profile 45 days, explicit 7 days, configured default 21 days, no configured term 30 days. Assertions include captured profile, term, due date and early-payment discount evidence.

2. **AP draft date edit selected new profile defaults but retained the old captured profile ID.** `VendorInvoiceService.UpdateCoreAsync` now saves the resolved role/profile with the new invoice date. Added `Update_accounting_date_captures_effective_profile_and_preserves_explicit_choices` in `CanonicalVendorInvoiceBusinessPartnerTests.cs` for September/October approved versions, default 60-day versus explicit old 30-day term, retained explicit line account and persisted profile ID. Existing posted-invoice immutability guard remains.

3. **AR customer projections and credit eligibility used legacy terms/credit limits.** `CustomerService` now resolves current approved profiles using the shared canonical policy, batching lookups for a customer list. Its contracts have no as-of date parameter, so these are explicitly current UTC-date defaults. Customer lookups and credit checks no longer use legacy partner values. Inactive/unready customer identities and historical balances remain readable, but cannot supply eligible credit or a default term. New `CanonicalCustomerProfileReadTests` checks approved 500 versus legacy 9000 credit, profile 45 versus legacy 90 days, ignored future version, draft/future/inactive/foreign-profile failures, and non-approval even for a zero-amount credit check when unready.

4. **AR draft date changes retained the old profile and could fail posting against its expired effective window.** Editable date changes now resolve and capture the profile for the new accounting date. The update contract has no term selector or marker distinguishing accepted explicit terms from prior defaults, so an already saved term and its accepted days/discount rate remain intact. An absent term receives the new profile/configured default. Explicit due dates are retained; absent due dates on date changes are calculated from the retained/resolved days. Discount deadlines move using the accepted offset from the invoice date. `UpdateInvoiceDate_ShouldCaptureEffectiveProfileAndPreserveAcceptedTerms` verifies both retained-term and newly defaulted-term cases across two approved periods. AR create's informational credit-exposure warning now reads its captured profile limit too.

5. **AP payment-term lookup confused a descriptive label with applicability.** Create/update/defaults passed the literal `Business Partner AP profile` to a helper comparing the value against `PaymentTerm.ApplicableTo`; approved Supplier/Contractor terms were rejected while `All` terms worked. The helper now receives the actual canonical role enum. Supplier accepts the established Vendor alias; Contractor accepts Contractor/All rather than Supplier/Vendor terms. Ten new cases in `CanonicalVendorInvoiceBusinessPartnerTests` cover defaults → create → update for role-specific, All, alias and configured fallback terms, and reject terms for another role before creating an invoice.

6. **AP first-post profile validation was weaker than AR.** AP invoice/payment supplier resolution formerly checked only partner identity, active status and blacklisting. It now validates the exact captured tenant-owned role/profile, approved status, accounting-date window and applicable WHT readiness through `BusinessPartnerFinanceProfilePolicy.ResolveAp`. A different approved profile is never substituted. Already-posted paths skip this additional first-post check, preserving existing replay/settlement semantics; existing partner identity checks remain. `FirstPosting_RequiresTheCapturedApprovedApProfile_ForTheDocumentDate` adds eight cases in each AP invoice/payment test class: missing/draft/expired/future/foreign-tenant/wrong-role profile, inactive/wrong-type role. Each fixture also carries an approved replacement to prove fail-closed capture behavior. Existing duplicate-post tests supersede the captured profile between initial posting and retry.

7. **AP expense fallback consumed the obsolete mutable partner account.** It now uses explicit line GL → invoice expense → exact captured approved/effective AP profile default. Existing inventory/fixed-asset rules remain. For posted invoices without a custom distribution, fallback uses the original source-line expense account before any profile default, requiring the matching tenant/source posted unreversed journal and unambiguous posted account evidence. `ExpensePosting_UsesExplicitLineThenInvoiceThenCapturedProfile_NeverLegacySupplier` posts three deliberately different precedence scenarios and checks replay after changed/removed profile defaults. `ExpensePosting_RejectsMissingCapturedProfileExpense_EvenWhenLegacyDefaultExists` proves the old supplier account cannot mask missing configuration.

Tests were added but were not run by this audit agent; coordinated build/test execution remains pending and its evidence belongs in the main regression checklist.

## Open findings needing focused follow-up

### A. Historical custom-distribution replay needs preserved original basis

A saved custom distribution contains its final split rows and a hash of the pre-distribution account basis, not a complete original basis snapshot. If the captured profile/default used for that basis disappears or changes after posting, the final GL split accounts cannot reconstruct the original base account. Existing basis validation must not be bypassed. These retries now return `AP_INVOICE_DISTRIBUTION_HISTORY_REQUIRED`, instructing Finance to review historical evidence rather than reset a posted distribution. The original journal is retained. Transparent retry for those historical cases requires immutable base-distribution snapshots or a Finance-owned exact replay API.

`DistributionEdit_PostedProfileBasedSplits_RequireHistoricalBasisWhenProfileChanges` covers both changed and missing profile evidence after posting a split and asserts no duplicate journal/transactions. These are explicit fail-closed limitation tests, not proof that transparent historical replay is implemented.

### B. Historical role inactivation and Sales credit-note policy require broader acceptance

The AP changes deliberately apply canonical readiness only before first posting. Existing partner-active checks still run in some posted settlement paths, and customer adjustment reversal resolves current counterparty readiness; complete historical inactive-role/profile acceptance is not established here. Sales credit notes also retain their distinct returns contra-account policy and lack original invoice-line/tax-component lineage for arbitrary exact revenue/tax reversal. Their AR-control mismatch is corrected separately; see `FINANCE_RETURNS_ACCOUNT_SOURCE_AUDIT.md` for exact behavior and remaining canonical Sales profile-readiness gap.

- `CanonicalVendorInvoiceBusinessPartnerTests`: canonical identity capture, missing effective profile, ambiguous supplier/contractor role, new date-change cases.

- `ApInvoicePostingMigrationTests` and distribution/tax partials: balanced invoice/account/tax/distribution behavior; newly added captured-profile readiness, expense precedence, original-account replay and historical custom-basis fail-closed cases.
- `ApPaymentPostingMigrationTests` plus `.PartnerDefaults`: selected-bank authority, no supplier AP override, original discount account on retry, confirmed invoice WHT, frozen cross-currency settlements, reversals, duplicate protection and newly added exact captured-profile first-post guards.
- `ArReceiptPostingMigrationTests` plus `.PartnerDefaults`: Finance/bank account authority, original discount replay, immutable ledger/allocation/bank reversal and duplicate reversal.

Passing these tests establishes only the exercised service behavior. Complete acceptance still requires SQL-backed migration/constraint checks and authenticated visible UI → API → GL/subledger checks on representative current profiles, invoices, receipts/payments, corrections and tenant/permission failures.
